# Marketing email — Inverted Check (2026-10-06)

> **Premise.** The feature on `claude/marketing-email-preferences` (PR #92) shipped green: type-check, lint, `arch:check`, 2,909 tests, eight mutation checks, rendered screenshots and one live opt-out. Every one of those checks was confirmatory, built by the same author, from the same assumptions. This check is **falsifying**. It assumes each claim is wrong and attacks it with a different instrument from the one that produced it:
>
> - the live Resend API instead of the test doubles;
> - a real browser instead of jsdom;
> - the deployed preview instead of local code;
> - the vendor's raw documentation instead of a summary of it.
>
> Method and grades follow `workspace-ui-inverted-check.md`: **BUG** (broken behaviour), **DEBT** (works, will cost later), **HOLE** (unverified), **WRONG** (a stated claim is false).

## Why this was warranted

The unit tests for the Resend adapter run against a double whose shape I wrote: field names, error names, behaviour. The double agreed with the code because one person wrote both. No test had ever exercised `addContact` against Resend, and the only live opt-out had touched a lowercase address.

## Clean (probe could have failed and did not)

- **DNS:** `updates.metricgymos.com` exists (NOERROR, no NXDOMAIN for receivers' sender checks), and DMARC falls back to the apex `p=none`.
- **Vendor quotes:** both sentences quoted in `marketing-email.md` (topic `opt_in` semantics, global unsubscribe) appear verbatim in Resend's raw docs.
- **Deployed preview:** a bad token gets 400 `INVALID_LINK`, a truncated body gets 400, and `/unsubscribe` is public and `noindex`. The preview carries both variables (otherwise 503).
- **`addContact` live:** created → unchanged → added to a second audience; `not_found` is the real error name.
- **Demo form:** clicking "privacy policy" inside the consent label opens the policy in a new tab and leaves the box unticked.
- **Test isolation:** integration tests share `tests/setup.ts`, which deletes the key; no E2E spec submits the demo form.
- **SDK logging:** the SDK logs API errors only when `NODE_ENV` is not `production`, so Vercel logs carry no 404 noise.
- **Migration history:** the migration was recorded as `20261005202909` against the repo's `20261006000001`, the project's known pattern; the SQL is idempotent.

## What this says about the method

Three of the four bugs (F1, F2, F3) were invisible to the original test suite for the same reason: **the double was written from the same belief as the code.** Only the live API, or the vendor's source, could contradict that belief.

The fourth near-miss was mine: F2b. While falsifying F2, I treated a single early read in an eventually consistent system as proof that a write had failed, and very nearly committed a false vendor defect into code comments. Two probes contradicting each other was the signal. A negative read needs a time series before it is believed.
